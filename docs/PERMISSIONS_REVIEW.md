# 当前版本测试：班长授权及关联问题

测试日期：2026-10-09。应用源码基线为本地提交 `998e1f9`，后端声明版本 3.4.0。

## 结论

用户报告的现象已在源码后端与现有 Windows EXE 上分别复现：为班长岗位勾选“创建任务”并点击保存，页面收到成功响应并关闭弹窗，但权限表没有保存该权限。刷新页面、退出重新登录均不能使这次授权生效。这是保存路由失效，不只是权限列表未刷新。

本轮任务是测试和定位，应用源码、HTML、EXE、实际配置及业务数据库没有修改。新增诊断脚本，并为测试夹具增加独立 EXE 测试模式。没有上传这些测试修改到 GitHub。

## 确认问题（按优先级）

### [P1] 岗位权限保存请求被错误路由截获

位置：`TeamToDo V1.1/server.py:1609`、`static/index.html:2707`。

`PUT /api/roles/<id>/permissions` 先命中 `path.startswith("/api/roles/")`，被传入 `_api_roles_update("permissions", body)`。由于请求体只有 `permissions`，该函数没有任何更新字段，直接返回 `{"ok": true}`。后面的 `_api_role_permissions_update()` 永远没有机会执行。

浏览器实际点击复现：创建只有 `task.feedback` 的班长测试岗位，勾选 `task.create` 后保存；响应 HTTP 200，回读权限仍只有 `task.feedback`，完整刷新后卡片也不包含创建权限。班长重新登录后创建任务仍返回 HTTP 403。前端保存逻辑也没有检查业务返回是否成功，会放大类似失败为“已更新”提示。

建议：先匹配具体权限子路由，再匹配岗位本身的精确路径；检查两个保存响应，只有成功落库后关闭弹窗并更新列表。

### [P1] 无删除权限的普通成员仍能删除任务

位置：`TeamToDo V1.1/server.py:3352`。

`_api_tasks_delete()` 只有登录校验，直接按任务 ID 删除，没有验证 `task.delete`、任务可见范围或所有权。

测试：只有 `task.feedback` 的普通用户删除管理员创建的测试任务，接口返回 HTTP 200；管理员随后读取任务得到 HTTP 404，确认数据确实已删除。隐藏前端删除按钮不能阻止接口操作。

建议：在后端同时验证删除权限与任务访问范围，并对拒绝请求验证任务仍存在。

### [P1] 账号停用、管理员降权未立即使旧会话失效

位置：`TeamToDo V1.1/server.py:1003`、`:1242`、`:1256`。

`session_get()` 仅检查令牌是否存在及过期；`require_auth()` 不检查账号是否已停用，`require_admin()` 仍以登录时缓存的系统角色判断管理权限。

分别复现：

- 管理员停用一个已有创建权限的用户后，该用户使用原令牌创建任务仍得到 HTTP 201。
- 将一个已登录管理员降为普通用户后，原令牌读取用户管理接口仍得到 HTTP 200，而应拒绝。

建议：请求时核对账号状态和当前角色，或在停用、降权、改密码时撤销相应会话。每台客户端维护独立会话，针对共享数据库的变更必须在各客户端请求时生效。

### [P2] 已打开页面不会同步其他用户授予的权限

位置：`TeamToDo V1.1/static/index.html:1571`、`:2730`。

同步循环刷新业务列表，但没有重新读取当前用户的权限；`refreshMe()` 只在本页面保存岗位时调用。其他客户端修改岗位或用户岗位分配后，班长页面的 `me.permissions` 和按钮可见性仍保留旧值。

为独立验证这一问题，测试通过创建一个含 `task.create` 的新岗位并调整用户岗位分配，绕开上面的权限保存路由错误。接口 `/api/users/me` 已返回新权限，但已打开的班长页面等待七秒后 `hasPerm('task.create')` 仍为 false；完整刷新后才变为 true。

建议：将当前用户权限同步纳入页面同步生命周期，权限变化后更新按钮及受权限约束的列表，保留正在编辑的内容。

### [P2] 子任务进度接口仍返回 HTTP 500

位置：`TeamToDo V1.1/server.py:3374`、`static/index.html:2423`。

`_api_task_progress()` 连接任务表和用户表后选择未限定表名的 `id`，SQLite 报 `ambiguous column name: id`。查询还选择了未定义的 `assignee_name`；返回格式把 `subtasks` 放在 `progress` 中，前端却读取顶层 `r.subtasks`，因此只修 SQL 还不足以恢复显示。

本轮对有效测试任务调用进度接口，源码和 EXE 均返回 HTTP 500。这是之前记录过但仍存在的独立问题。

建议：修正查询字段别名，统一前后端数据格式，并以包含未完成、已完成子任务的真实请求验证统计和列表。

## 测试方法与结果

运行：

```text
node tests/permissions_review.cjs
node tests/permissions_review.cjs --exe
node tests/live_refresh.cjs
```

诊断脚本使用真实浏览器点击“保存”，结合 HTTP 回读及重新登录验证。两种后端模式各自记录 9 项失败检查，归并为上述 5 类问题；脚本发现问题时按设计退出码为 1，执行环境失败则为 2。

源码模式使用临时数据库和随机本机端口的真实 HTTP 处理器。EXE 模式将现有 `TeamToDo.exe`、静态资源及 schema 复制到临时目录，明确指定临时数据库及随机本机端口，关闭浏览器自动打开和软件自动更新。启动窗口隐藏，结束后清理测试进程及临时文件。两种模式均未使用生产配置或共享数据库。

已有实时刷新回归测试通过：跨会话任务及反馈更新、编辑草稿保护、大屏更新、失败恢复、远程删除、搜索筛选保留、隐藏页面暂停及重新可见时刷新。此次授权问题与数据刷新机制是两个不同问题。
