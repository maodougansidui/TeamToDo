# 页面实时刷新：审查与验证记录

检查日期：2026-10-07。

## 原因与修复范围

对应用目录的前端、后端、建表文件、配置模板、启停脚本、部署说明和已有日志进行了检查。原页面的 `showApp()`、`switchTab()` 和本人保存操作会读取任务；`startUpdateWatch()` 每五分钟检查的是软件更新包。原代码没有业务数据同步循环。由于每个客户端拥有独立本机服务，共享数据库中其他客户端的写入无法主动通知当前页面。

浏览器验证中，会话 B 更新任务后，原页面等待四秒仍显示旧标题。修复页面在下一轮同步后显示新标题和状态。修复使用现有 GET 接口，没有数据库表、触发器或迁移变更，也没有进程内通知机制，因此数据读取不依赖修改来自哪一个本机服务。

应用变更集中在 `TeamToDo V1.1/static/index.html`：

- 登录恢复后开始同步，退出时停止。
- 每轮完成后延迟三秒读取当前栏目；同一时刻只运行一个自动同步循环。
- 可见性、焦点及联网事件触发即时同步。
- 编辑表单、筛选面板和拖拽期间暂停；反馈详情更新保留草稿。
- GET 禁用浏览器缓存，三十秒超时后释放请求，后续循环可以重试。
- 任务列表按当前筛选读取，用请求序号和查询条件校验丢弃过期结果，变化时才重新渲染。
- 已删除或不可见任务的详情关闭；异步详情响应校验任务 ID。
- 当前栏目支持任务、大屏、人员、组织、岗位和台账；待确认反馈数量定期更新。

## 回归证据

`tests/fixture_server.py` 导入真实后端模块，显式设置独立临时数据库，调用建表和迁移后在随机本机端口提供 HTTP 服务。它不读取部署配置，也不启动生产 EXE。`tests/live_refresh.cjs` 使用真实浏览器和两个登录会话。

已验证：

1. 老版本能复现其他会话修改后页面不更新。
2. 修复后远程任务标题、状态自动更新。
3. 打开的详情与新反馈自动更新，未发送反馈不丢失。
4. 编辑任务时保留草稿，关闭弹窗后恢复同步。
5. 大屏统计在其他会话新增任务后更新。
6. 请求失败后能继续同步，联网事件触发刷新。
7. 远程删除后任务从列表消失，过期详情关闭。
8. 保留任务搜索条件，其他任务不混入筛选结果。
9. 隐藏页面暂停业务读取，重新可见时立即读取。
10. 浏览器无未捕获脚本错误；本地业务数据库哈希与测试前一致。

## 已有独立问题与边界

已有日志和代码均表明 `server.py` 的 `_api_task_progress()` 查询存在 SQL 错误：连接 `tasks` 与 `users` 后直接选择未限定的 `id`，导致 `ambiguous column name: id`；同一 SELECT 还使用了没有正确定义的 `assignee_name`，后端返回的 `subtasks` 位置也与前端判断不一致。该问题早于本次修改，不是实时刷新缺失的原因。本次保留原有子任务汇总行为，没有把此错误接口加入周期轮询。

这是针对实时刷新问题及修复差异的审查，未完成整个系统的安全审计。人员、组织、岗位、台账和待确认反馈已有同步接入，但本记录的端到端变更测试重点是任务、反馈、大屏和同步生命周期。共享盘上数十或上百台客户端并发时的容量、旧浏览器及实际 Windows EXE 运行环境仍需部署方验证。
